# TCP300II カード R/W 通信プロトコル メモ

出典: スター精密「TCP300IIシリーズ コマンド仕様書」(全67ページ)を本番機で確認し要点を書き起こし。
仕様書本体はメーカー著作物のためリポジトリには含めない。

## 接続・機種
- 本番機実測: TCP300II = 仮想COM **COM3** / VID_0519 PID_0002 / SMJUSB・SMJUSBCOM(v5.0.0.0)
- **本機は「300」= 1トラック磁気ヘッド**(TCP300II)。読み書きは **トラック2 のみ**(パラメータ `'2'`)。
- 制御は pyserial で COM3 へシリアル通信(OCX不要)。CT-S601(レシート)は COM7。
- 排他制御: 仮想COMは1プロセス専有。宝飾ナビ稼働中はトキワから開けない。
- ボーレート: メモリスイッチ(通信設定 90h)依存。USB仮想COMは無視する場合あり。既定9600で試し、駄目なら要調整。

## フレーム / 制御キャラクタ(3-4, 3-5)
| 記号 | コード | 意味 |
|---|---|---|
| STX | `02h` | テキスト開始 |
| ETX | `03h` | テキスト終了 |
| ACK | `06h` | 正常応答 |
| NAK | `15h` | 再送要求 |
| DLE | `10h` | 拒否応答 |
| LF  | `0Ah` | 印字改行 |
| ESC | `1Bh` | エスケープ開始 |

- **コマンド転送**: `STX | コマンド | データ列 | ETX | BCC`
- **レスポンス転送**: `STX | コマンド | ステータス | データ列 | ETX | BCC`
- **BCC = コマンドからETXまでの排他的論理和(XOR)**。値域 00h〜FFh。
- データ列長は 1024 バイト以内。

### ハンドシェイク(3-1〜3-3)
1. ホスト → コマンドブロック送信
2. R/W → `ACK`(受理) / `NAK`(再送要求→再送) / `DLE`(拒否→中止)
3. R/W がカード処理(カード未挿入なら挿入を待つ。ACKは処理前に返る)
4. R/W → レスポンスブロック送信
5. ホスト → BCC照合し `ACK`(一致) / `NAK`(不一致→再送要求)
- リトライ既定2回(計3回)。リセット `5Fh` は実行中でも発行可(初期化約3秒)。
- 挿入待ちのキャンセルは `54h`(カード挿入待ち状態解除)。排出待ち解除は `55h`。

## 主要コマンド一覧(3-11) ※本機は「300」=1トラック
### 磁気リード
| コード | 内容 | フォーマット |
|---|---|---|
| `24h` | トラック&フォーマット指定リード | `STX 24h [トラック] , [フォーマット] ETX BCC` |
| `28h` | 同上(カード無しステータス付) | `STX 28h [トラック] , [フォーマット] ETX BCC` |
| `22h` | **第2トラックリード(自動識別)** | `STX 22h ETX BCC`(BCC=`21h`) |
| `21h`/`23h` | 第1/第3トラックリード(310のみ) | 1トラック機は不可 |
| `26h` | 第2トラックリード(カード無しステータス付) | `STX 26h ETX BCC` |
| `2Ch`/`2Ah` | バッファリード(搬送せず前回値取得) | - |

- トラック指定: `'1'`/`'2'`/`'3'`。**1トラック機(300)は `'2'` のみ有効**。
- フォーマット指定: `'0'`=7bit(JISX6302) / `'1'`=6bit(ISO7811/2 T1) / `'2'`=4bit(ISO7811/2 T2,70bpi) / `'3'`=4bit(T3) / `'4'`=逆7bit。
- リードデータ列に開始/終了符号・LRC・パリティは含まれない。7bit=0〜69byte(01h〜7Eh, 02h/03h除く)。
- `22h`等は開始符号で自動フォーマット識別。確実性優先なら `24h`(フォーマット明示)推奨。

### 磁気ライト(2段階: データ設定 → 書込実行)
| コード | 内容 | フォーマット |
|---|---|---|
| `3Ch` | 第2トラックデータ設定 | `STX 3Ch [ライトデータ列] ETX BCC` |
| `38h`/`39h`/`3Ah` | 7bit T1/T2/T3 データ設定 | - |
| `35h`/`36h`/`37h` | 逆7bit T1/T2/T3 データ設定 | - |
| `31h` | **磁気ストライプライト→待機** | `STX 31h [ライトトラック指定] ETX BCC` |
| `32h` | 同上(カード無しステータス付) | - |

- ライトトラック指定: `'2'`=トラック2書込許可(1トラック機はこれのみ)。他 `'1'`〜`'7'` は組合せ。
- 手順: (1)`3Ch`で第2トラックのデータ設定 → (2)`31h`(param `'2'`)で書込実行。開始/終了符号・LRC・パリティは自動付加。書込後は自動ベリファイ。失敗時はリトライ(既定2回)。

### 印字・消去(券面リライト) — 詳細確定(2026-07-29 仕様書4-2を書き起こし)
| コード | 内容 |
|---|---|
| `41h` | 印字文字データ設定(下記詳細) |
| `40h` | 印字展開バッファクリア(`STX 40h ETX 43h`) |
| `49h` | バッファクリア(印字展開+イメージ登録の両方) |
| `43h`/`4Dh` | 外部イメージ展開(ライン/ブロックモード。8ドット=2キャラクタのテキスト化) |
| `44h`/`45h` | 全角/半角 外字フォント登録(揮発・最大16個) |
| `46h` | 消去+印字→排出(下記詳細) |
| `47h` | 印字→排出 / `48h` 消去→排出(46hのパラメータで同等動作可・非推奨) |
| `4Eh` | バーコードデータ設定 |

#### 41h 印字文字データ設定(★券面印字の本体)
- フォーマット: `STX 41h [印字制御ヘッダー列][印字テキストデータ列] ETX BCC`。**最大1024バイト**、
  複数回送信可(展開バッファに追記される。クリアは40h/49h/電源断のみ)。
- **印字制御ヘッダー列** = `配置方向 , X座標 , Y座標 ,` (一括省略可。省略時は前回の続きから)
  - 配置方向: `'0'`縦置き+上書き / `'1'`横置き+上書き / `'2'`縦置き+重書き / `'3'`横置き+重書き
  - X,Y = **テキスト左下端**の座標。横置き: X 0〜479, Y 0〜319 / 縦置き: X 0〜319, Y 0〜479
  - **Y最小は23**(左下端基準のため)。**テキストにカンマを含む場合はヘッダーを省略しない**こと。
- テキスト: 半角ANK + 全角(JP仕様=Shift-JIS)。`LF(0Ah)`=復帰改行(X座標原点へ)。
- **ESCシーケンス**(テキスト中に埋め込む):
  | シーケンス | 内容 |
  |---|---|
  | `ESC E11/E12/E21/E22` | 文字サイズ 通常/横倍/縦倍/縦横倍 |
  | `ESC Xnnn` / `ESC Ynnn` | 座標指定(3桁) |
  | `ESC Snn` / `ESC snn` | 全角/半角換算でn文字右へ(2桁) |
  | `ESC Lnn` | n行下へ(2桁) / `ESC Mn` 行間ドットスペース(1桁) |
  | `ESC Dn` / `ESC dn` | 全角/半角の文字間ドットスペース(1桁) |
  | `ESC W1/W2` `ESC V1/V2` | 幅/高さの倍率 |
  | `ESC B0/B1/B2` | ANK線幅(細/強調/強強調ゴシック) |
  | `ESC J0/J1` | ANKを全角/半角フォントで印字(JP仕様のみ) |
  | `ESC Gn` / `ESC gn` | 全角/半角 外字フォント展開(n=0〜F) |
- 範囲外に展開すると 51h(展開バッファオーバーフロー)。上書き指定(0/1)は後勝ち。

#### 46h 消去+印字→排出
- フォーマット: `STX 46h [排出制御],[消去制御],[印刷制御] ETX BCC`(パラメータは省略可)
  - 排出: `'0'`=前方待機(処理対象のまま) / `'1'`=排出(引き抜き待ち)
  - 消去: `'0'`=しない / `'1'`=する ・ 印刷: `'0'`=しない / `'1'`=する
  - **全省略 = 消去+印刷→排出**(従来互換)。例: `46h '1','1','0'` = 消去のみ→排出(券面無効化)
- 待機カードがあれば即実行、無ければ**挿入待ち**(キャンセルは54h)。
- 印字後もバッファは保持される(同じ内容を何枚でも印字可)。処理時間はカード・温度で変動。

## 実機テスト結果(2026-07-12 本番機・荒川様見本カード)

- **読み取り成功**。`59h`ステータス要求→なぜかDLE拒否(要調査・実害なし)。
  `22h`リード→ACK→カード吸入→レスポンス(status=20h)。排出も`50h`で動作。
- **第2トラックの実データ = 60文字の英数字**(大文字小文字混在):
  `00Ua4Z0sE3WmDjqxC3OuE30stJimDWwQC3ODdJ0s20ci73Wu00Sv6610MQV0` (7bit JISフォーマット)
  → 平文の会員番号ではなく**宝飾ナビ独自のエンコード済みデータ**。
  券面(荒川涼太/発行2013.09.09/期限2018.09.12/ポイント997)との対応は未解読。
- 仕様書の警告どおり**自動識別(22h)が一度意図せぬフォーマットで応答**
  ("000000"の短フレーム)→BCC不一致→再送で正フレーム、という揺れを実測。
  → ドライバを修正: フォーマット明示リード24h(`2,0`=7bitJIS)を既定に、
  BCC不一致はNAK→再受信リトライ、コマンドエコー不一致フレームは読み飛ばし。
## 3回目実測(2026-07-12) — ★磁気フォーマット確定

- **逆7bit指定リード(24h '2,4')が status=正常** → **宝飾ナビの磁気書込は
  逆7ビット(JIS X 6302 逆方向)で確定**。読取データは自動識別時と完全一致。
- トキワが将来書き込む際は 逆7bitデータ設定(36h=第2トラック)→ライト(31h/'2') を使う。
- 排出50hはこの回もDLE拒否(リトライ3回とも)。**リセット5Fhの初期化で
  カードは排出された**(リセット応答=20h正常)。以後の排出DLEはカード無しのため無害。
  → card_test は排出失敗時「リセット→取り出し案内」に簡素化。
  50hがDLEされる根本原因は未解明(読取後の装置状態依存とみられる)。
  実運用の会計フローは「消去+印字→排出(46h)」系を使う予定のため実害は限定的。

### 2枚比較による構造解析
`0s` を区切りとみなすと両カードとも4フィールドに分かれる:

| # | カード1(荒川) | カード2(浦) | 観察 |
|---|---|---|---|
| F1 | `00Ua4Z` | `00VQ4J` | 先頭`00`共通。顧客毎に変化(顧客ID?) |
| F2 | `E3WmDjqxC3OuE3` | `ebOmDjrBC3OuE3` | **末尾`C3OuE3`一致**。`Dj`も同位置 |
| F3 | `tJimDWwQC3ODdJ` | `spqmDhIPC3OZYp` | `C3O`が同位置。日付系? |
| F4 | `20ci73Wu00Sv6610MQV0` | `20dI7pWu00Sw6?10MncS` | **先頭`20`・`Wu00S`一致**。ポイント/日付? |

- 同一位置に同一文字が現れる=**位置依存の換字(固定キー)エンコード**の可能性が高い。
  平文候補: 顧客ID・店舗コード・発行日・有効期限・ポイント・最終来店日。
- **有効期限の法則発見**: 期限=最終来店日+4年とみられる
  (荒川: 最終来店2014.09.12→期限2018.09.12 / 浦: 2026.07.12(本日宝飾ナビで使用?)→2030.07.12)。

### 顧客キー対応の方針
- (A) 換字表の完全解読 — サンプル追加で可能だが工数大。
- **(B) 推奨: 「初回挿入で紐付け→トキワ形式に書き換え」方式**
  1. トキワ稼働後、カード挿入→磁気60文字を不透明キーとして検索
  2. 未登録なら店員が顧客を選んで紐付け(初回のみ)
  3. その会計でカードを**トキワ自身の単純形式(例: 顧客ID平文)で磁気を書き換え**+券面リライト
  → 2回目からは完全自動。**宝飾ナビ形式の解読が一切不要**になり、カードは来店の度に自然とトキワ化される。

## ★磁気ライト実機検証 確認済み(2026-07-18 本番機・予備カード)

**排出→再挿入後の読み取りでも一致(RESULT=PASS・再挿入確定)。カード書込が実機で
本当にできることを確認。** これで移行最大の未検証点(カード書込)がクリアし、方式Bが成立。

確定ログ(2回目・修正版ツール)の要点:
- `36h` 逆7bitデータ設定「TOkiWATest」→ 正常(20h)
- `31h`(param '2')磁気ライト → 正常(20h)
- (参考)排出前 `24h '2,4'` 読み → "TOkiWATest"(※これ単体は確定材料にしない)
- 排出`50h`はDLE拒否 → リセット`5Fh`で排出 → **カードを物理的に入れ直し**
- **入れ直し後の `24h '2,4'` 読み → "TOkiWATest"(書込内容と完全一致)**
  → 抜き差し後も読める=バッファ由来ではなく磁気ストライプに実書込されている証拠。

確定事項:
- 書込書式は **逆7bit(データ設定`36h`→書込実行`31h`/'2')**、読み戻し`24h '2,4'` で往復一致。
- 実運用: 会計時に「顧客ID等の平文をトキワ独自形式(逆7bit)で書込」→次回以降カード挿入で自動呼出。
- 検証ツール `hardware/card_write_test.py` は「書込→排出→再挿入→確定読み」の手順。

周辺機器の検証状況: カード読取✅ / **カード書込✅(再挿入確定)** / レシート印字✅ / ドロワー✅
→ 残るフェーズ①は「機器を実アプリのフロー(会計→印字+ドロワー+カード書換 / カード挿入→顧客呼出)に組み込む」実装。

### (参考)1回目のテストが未確定だった理由
最初のテストは **カードを排出せず入れたまま読み戻した** ため、24hリードが直前の書込バッファを
返しただけの「見かけ上の一致」の可能性があった。またカード個体に磁気ストライプが無い等の
条件だと書込が通らない。→ ツールを排出→再挿入方式に修正し、上記2回目で確定した。
以下は当時の記録(経緯として保持):

**装置は書込成功(20h)を応答し、読み戻しも一致(スクリプトはPASS表示)したが、
排出前の読み戻しだったため確定できなかった(要再検証)状態だった。**

理由: このテストは **カードを排出せず入れたまま読み戻した** ため、24hリードが
「直前に36hでセットした書込バッファ」をそのまま返しただけ=**見かけ上の一致(誤判定)**
の恐れがある。磁気書込は不可視(券面印字は未実施)なので目視でも確認できない。
実機を見ていた店主の観察では「吸込OK→カード面リセットNG→書込NG→吐出OK」で、
物理的な書込動作が行われていないように見えた。

実測ログ(`hardware/card_write_test.log`)の要点:
- `59h`ステータス要求 → 正常(20h, "000000")
- `36h` 逆7bitデータ設定「test」 → 正常(20h)  ※これはバッファへのセットに過ぎない
- `31h`(param '2'=トラック2)磁気ライト実行 → 装置応答は正常(20h)
- `24h '2,4'`(逆7bitリード)→ 正常(20h)・データ="test"  ※排出前なのでバッファ由来の疑い
- 排出`50h`はDLE拒否(3回)→ リセット`5Fh`で排出

★確定に必要なテスト(次回): **書く→カード排出→同じカードを入れ直す→読む**。
入れ直して読んだ値が一致して初めて「磁気に本当に書けた」と言える。
→ `hardware/card_write_test.py` を「書込→排出→再挿入→確定読み」の手順に修正済み。

書込が本当に失敗していた場合に疑う点:
- 予備カードに磁気ストライプが無い/非対応(そもそも書けない)。→ 磁気付きカードで再試験。
- 逆7bit(36h)ではなく別書式が必要。→ スクリプトの書式2(7bit)でも試す。
- メモリスイッチ(通信/書込設定 90h/91h)で書込が無効化されている可能性。
- 券面リライト(サーマル印字)は別コマンド(46h/47h系)。今回は磁気のみで券面は未変更。

# トキワ 正式運用ロードマップ(目標: 2026年9月 正式運用開始)

作成: 2026-07(開発中)。9月に店舗で正式運用を始めるための逆算スケジュール。
方針: **9月はローカル(店内)で正式運用開始 → クラウド移行は10月以降**の2段構え。
理由: クラウドはログイン認証・HTTPS・暗号化・オフライン同期・セキュリティ3点が
前提で9月に全部は詰め込みすぎ。データ消失対策(元々の動機)は店外への自動バックアップで
当面カバーし、クラウドの本領(スマホ/iPad・複数店舗)は運用安定後に。

## クリティカルな依存関係(遅れると全体がずれる)
1. **実データの入手** — 2026-07中旬、宝飾ナビの会社が吸い出し作業中。今日〜明日に用意予定。
2. **宝飾ナビからの吐き出し形式** — xlsx想定(デモと同じ11台帳形式なら分析ツールがそのまま使える)。
   CSVなら文字コード確認(Shift-JIS/UTF-8)。
3. **カード磁気との対応表** — 磁気60文字(宝飾ナビ独自エンコード)と会員番号の対応表が
   吸い出しに含まれるか。あればカード連携移行が楽。無ければ「初回挿入で紐付け」方式。
4. **カード書込の実機テスト** — 店の営業時間外が必要(①で早めに)。

## データ移行の手順(データ受領後すぐ)
1. xlsx一式を `data/real/` に置く(.gitignore済み。GitHubには上がらない・PC内のみ)。
2. `python scripts\analyze_real_data.py` を実行 → `data/real/分析レポート.md` 生成。
3. レポートを共有 → 孤児データ/重複/商品参照切れ/ポイント不一致/処方箋混入を確認。
4. クレンジング方針を合意 → 本番用インポート(import_to_sqlite.py を実データ形式に合わせて調整)。

## 新機能の実装優先順位(2026-07-15 相談で確定。詳細は docs/feedback-backlog.md)
業務フローの入口(商品登録)でつまずくと後工程を何度もやり直すことになるため、
**商品写真を最優先**で一連の流れをテスト可能な段階まで作る。

| 順 | 機能 | 実装タイミング |
|---|---|---|
| **1** | **B-7 商品写真**(下記フローを一気通貫でテスト) | 表示確認と並行(⓪.5)。最優先 |
| 2 | B-1 返品・訂正(黒赤の積み重ねをやめ、最終状態のみ表示) | ⓪.5 |
| 3 | B-5 顧客ランク更新画面(月次自動+手動) | ⓪.5〜① |
| 4 | B-3 マスタ管理画面(カテゴリ分けで見やすく) | ① |
| 5 | B-2 ポイント追加・編集(カード連携) | ①(カード実機検証と同時) |
| 6 | B-4 検索・分析メニュー(誕生日/購入順位/ランク検索等) | ①〜②と並走 |
| - | B-6 修理写真 | B-7の基盤(アップロード機構)を共用するため実装コスト小。B-7直後でも可 |
| - | ロール別アクセス制御(仕入金額の非表示等) | ④(ログイン認証とセット。docs/access-control.md) |

### B-7 商品写真: テストすべき一連の流れ(業務フロー)
1. 商品仕入れ(現実世界。トキワはまだ無関係)
2. 仕入れ伝票と商品が手元に揃う
3. **商品登録**(仕入れ伝票を見ながら) ← ここで写真を登録
4. システムから**登録内容の確認・修正・削除**ができるか
   ← **削除時は写真ファイルも一緒に削除**(DB/ディスクを圧迫させない)
5. 顧客を登録し、その商品を購入 ← レジで商品にカーソル/クリックすると写真が見えるか
6. 顧客詳細の購入履歴でも、カーソル/クリックで写真が見えるか
7. **返品した時の動作確認** ← 在庫に戻った後も画像が正しく見えるか
この7ステップを通しで検証できる段階まで先に作り込む。

## 残作業の優先順位と使用量(2026-07-30 整理)

8月いっぱいをテスト期間にして9月から完全切替する前倒し案を検討した際の整理。
**優先度と使用量(Claudeのトークン消費)は連動しない**ため2軸で見る。

| 優先 | 項目 | 使用量 | 期限 | 使用量の理由 |
|---|---|---|---|---|
| **1** | **カード書込の実機検証**(難所) | ★☆☆☆☆ | 8月第1週 | 実作業は店側の物理作業。Claude側はテストスクリプト微調整と結果解釈のみ。ずれたら座標定数の往復が数回 |
| **2** | **自動バックアップ**(店外保管) | ★☆☆☆☆ | 8月前半 | scripts/backup_db.py が既存。日次スケジュール化のbatと保存先指定を足すだけ。画面変更ほぼ不要 |
| **3** | **レシート実機確認**(ロゴ画質・中央寄せ・最終行の切れ) | ★★☆☆☆ | 8月前半 | 実装済み。印字→写真確認→定数調整のループ。1回は軽いが往復が数回 |
| **4** | **実データのクレンジングと本番DB作成** | ★★★☆☆ | 8月中 | 実データは個人情報で開発環境から直接見られず往復が増える。21万件規模で想定外パターンが出るたびサイクルが回る |
| **5** | **並行運用での実務検証と微修正** | ★★★★☆ | 8月後半〜9月 | 1件は軽いが件数が多く積み上がる。集中すると跳ねる |
| **6** | **担当者マスタ+ログイン認証+ロール別権限** | ★★★★★ | 本来10月(④) | 最も重い。全画面に権限判定を入れる横断的変更＋ロール別の検証 |
| **7** | **オフライン同期(sync_queue)** | ★★★★☆ | 本来10月(④) | キュー・再送・二重登録防止・UIの横断実装。設計書はあるが実装は大きい |
| - | ロゴ高解像度化の仕上げ | ★☆☆☆☆ | 随時 | 画像差し替え→印字比較→定数(LOGO_DITHER等)を決めるだけ |

### 判明したこと: 優先度が高い項目ほど使用量は安い
最優先の1〜3は全て★1〜2。いずれも「実機を触る作業」で、物理作業は店側が行い
Claude側は結果を見て定数を直すだけのため。逆に使用量が特大の6・7はもともと10月(④)予定。
**「切替に必要なもの」と「使用量を食うもの」が分かれている**ので、8〜9月は安い作業に集中できる。
ただし6・7で本格的に使用量が必要になるため、**8〜9月に使い切らないよう配分する**こと。

### 前倒しする場合の条件(9月完全切替を狙うなら)
1. カード実機検証を8月第1週に実施し、**これが通るかで9月切替の可否を判断**する
   (切替日を先に固定すると、間に合わない時に無理な移行を強行することになる)
2. 自動バックアップを8月前半に完成させる ← 切替の絶対条件
3. 9月中は宝飾ナビを参照用に残す(元々の方針どおり。前倒し時はより重要)
4. サーバー停止・通信断時の紙運用手順を用意(checkoutは過去日付登録に対応済み)
5. 権限制御(項目6)が10月送りになる間、パートに仕入金額が見える状態になる。
   店内共有モードで凌ぐか運用ルールで縛るかを決めておく

### 機器の並行運用に関する制約(見落としやすい)
宝飾ナビ起動中はCOMポートを開けないため、**機器だけは並行運用できない**。
実機テスト・機器ONでの検証は営業時間外に限られる。8月の営業時間外の確保が前倒しの実質的な制約。

### 使用量を節約する運用
- 蓄積モードで複数の修正をまとめ、**動作確認(サーバー起動+Playwright)は1回に集約**する
- 実機系はユーザー主導なので安い。印字結果の写真をもらえば定数調整だけで済む
- 現場要望(項目5)は溜めてから一括で回すと往復回数が減る

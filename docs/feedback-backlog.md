- ⏳ **「ななし」(名無し)顧客運用 → 採用する。ただし「集計対象外」フラグで分析の歪みを防ぐ**
  (2026-07-16 相談で方針確定)。
  背景: 宝飾ナビでは「顧客必須」制約を回避するため、データをくれない一見客を全員
  「ななし」1顧客に集約していた(システム会社いわく「検索に引っかかるように」)。
  副作用として「ななし」1人に大量購入が積み上がり、顧客ランキング・平均購入額・累計等が
  歪む(架空の超VIP客が生まれる)。
  **合意した設計(名前必須のまま + ななし採用 + 永続フラグで除外)**:
  - 顧客マスタに **「集計対象外」フラグ**(仮: customers.exclude_stats)を追加。
    「ななし」や過去のバケツ顧客に1回付けておけば、以後すべての分析から自動除外される
    (レポートごとにチェックを入れ直す方式は付け忘れ・外し忘れが起きるため不採用)。
  - **除外の適用範囲は「顧客を1人の人物として数える集計」だけ**にする:
    | 集計 | ななしを含める? |
    |---|---|
    | 日次売上・現金合計(ホームのタイル/日報) | **含める**(実際に入った現金のため) |
    | 顧客ランキング・平均購入額・顧客の累計 | **除外**(1人の実在客ではないため) |
    → フラグはランキング等の顧客単位集計クエリにのみ `WHERE exclude_stats=0` を足す。
       日次のレジ締め金額(現金合計)には影響させない=現実の金額と一致したままにする。
  - 既存の is_test(検証ペルソナ)フラグとは別概念(is_testは開発用、exclude_statsは運用用)。
  - 実装タイミング: ランキング/平均等の画面は B-4(検索・分析メニュー)で未実装のため、
    除外ロジックは B-4 と一緒に組む。フラグ自体は顧客編集画面に先行追加も可能
    (先に「ななし」等へタグ付けを始められる)。どちらで進めるかは要確認。
  - 補足: customer_id は元々 NULL許容のため、フラグ運用と別に「顧客未選択のまま会計」も
    技術的には可能。ただし店の運用は「ななし」を選ぶ方式で統一する(現状のposError()の
    ブロックは維持でよい)。代引き手数料等レジ外の現金支出は上記「レジ入出金」機能で扱う。

- ⏳ **DBの桁数(列の長さ)設定について** → 結論: **今のままで問題ない**。
  - SQLiteの `TEXT` 型には(MySQL の VARCHAR(n) 等と違って)**文字数の上限が無い**。
    電話番号欄に20桁入れても技術的にはそのまま保存できてしまうのは事実で、バグではなく
    SQLiteの仕様。
  - **ディスク容量の心配は不要**: SQLiteは可変長で保存するため、列に長さ制限を付けても
    付けなくても、実際に入力された文字数分しか容量を使わない(短い電話番号は短い分だけ)。
    実データ62万行超を移行して `db/tokiwa.db` は65MB程度で、この規模ならまったく問題ない。
  - 桁数制限が効くのは「容量の節約」ではなく「入力ミスの早期発見」という別の目的。
    それが必要なら、DB側に制約を足すより**画面側の入力チェック**(例: 電話番号は
    ハイフン抜き最大11桁までなど)で防ぐ方が、エラー処理も分かりやすくシンプル。
  - 備考・メモ等の自由記述欄は、今のまま無制限で問題ない(容量的なデメリットが無いため)。
  - 対応: 今すぐの変更は不要。もし特定の項目(電話番号・郵便番号等)で入力ミス防止の
    チェックを入れたい場合は、個別に要望をもらえれば画面側のバリデーションとして追加する。

### B-7. 商品画像の登録 ★最優先
- 理由(2026-07-15 相談): 実業務のフローは
  「仕入れ→**商品登録(写真を登録)**→登録確認/修正/削除→顧客が購入(写真閲覧)→
  購入履歴でも写真閲覧→返品(在庫に戻った後も写真が見えるか)」という一連の流れで、
  **入口の商品登録でつまずくと後工程を何度もやり直す**ことになる。そのため他の新機能より
  先に、この一連の流れをテストできる段階まで作り込む。
- テストすべき一連の流れ(このまま検証項目にする):
  1. 商品仕入れ(現実世界。トキワはまだ無関係)
  2. 仕入れ伝票と商品が手元に揃う
  3. **商品登録**(仕入れ伝票を見ながら) ← ここで写真を登録
  4. 登録内容の**確認・修正・削除** ← **削除時は写真ファイルも一緒に削除**
     (DB/ディスクを圧迫させない。孤立画像ファイルを残さない)
  5. 顧客を登録し、その商品を購入 ← レジで商品にカーソル/クリックすると写真が見えるか
  6. 顧客詳細の購入履歴でも、カーソル/クリックで写真が見えるか
  7. **返品した時の動作確認** ← 在庫に戻った後も画像が正しく見えるか
- 宝飾ナビ側のデータ: d_item.strpicfilename(商品ごとの画像ファイル名) + d_item_pic(追加画像82件)。
- **画像ファイル本体を受領済み(2026-07-16。実測 8,094枚 / 738MB / 全て.jpg)**。
  置き場所は `data/real/images/`(.gitignore済み=GitHubには上げない・Mac内のみ)。
  `scripts/check_images.py` で照合した結果(2026-07-16):
  - 画像名を持つ商品 8,934件 → 実ファイル一致 **8,916件(99%)**。名前はあるが欠品18件のみ。
  - 追加画像(d_item_pic) 81/81件一致。孤立画像(未参照)約594件=表示不要。
  - **結論: d_item.strpicfilename のファイル名が実ファイルにそのまま対応**。
    B-7では「商品 → data/real/images/<strpicfilename>」で素直に紐づけ可能(ルール調整不要)。
- **画像の扱い方針(2026-07-16 相談。推奨・確定待ち)**:
  - **リサイズ+圧縮**: ブラウザ側(アップロード前にcanvasで長辺1000〜1200px+JPEG q80程度)。
    サーバーに画像処理ライブラリ(Pillow等)を入れずに済む=標準ライブラリのみ構成を維持。
    アップロードも軽くなる。1枚100〜300KB目安。
  - **正方形化**: 保存はクロップしない(宝飾品が切れるため)。元の縦横比のまま縮小して保存し、
    一覧表示だけCSSで正方形サムネにする(object-fit)。どうしても正方形保存が要る場合のみ
    余白パディング方式。
  - **保存先**: 画像は"ファイル"で保存し、DBには"パス/ファイル名"だけ記録(ロゴと同様)。
    DBにバイナリを入れない(肥大化・バックアップ重・配信遅を回避)。
  - 既存の宝飾ナビ画像(8,916枚)は元サイズのまま置き、B-7実装時に表示用の縮小キャッシュを
    生成するかは容量と表示速度を見て判断。
- 実装: products に画像パス(複数可)、商品詳細・在庫一覧・レジ・購入履歴でサムネイル表示、
  削除時は画像ファイルも削除。B-6(修理写真)とアップロード基盤(スマホ撮影対応)を共用。
  配信は /assets/logo.png と同様にサーバーの静的配信(専用ルート)で。容量対策で
  表示用は長辺1200px程度に縮小したキャッシュを作ることも検討。

### B-8. 仕入(商品)登録フォームの見直し(2026-07-15相談)
- **画面を2つに分ける**: 「仕入れ登録(宝石)」「仕入れ登録(宝石以外)」のタブ。
  - 宝石以外(メガネ・時計等)は宝飾関連の入力項目(中石・重量・color/clarity/cut等)が
    不要なので、**「ブランド」「品番」「その他」**のみのシンプルな項目にする。
  - 宝石側は現行のフォームのままで概ねOK(要望より)。
- **税区分の明確化+自動計算**: 仕入単価は**税別**入力、上代は**税込**表示。
  掛率の計算例として要望に挙がった数値: 仕入500円(税別)・上代1,100円(税込)・掛率50%。
  →逆算すると「仕入単価を税込換算(500×1.1=550円)してから上代(税込)で割る」で
  550÷1,100=50%になるため、**掛率 = 仕入単価(税込換算) ÷ 上代(税込) × 100** で実装する。
  現行の `updateNpRate()` は税抜同士で割っており、掛率の意味が実務の掛け率と食い違うため
  修正が必要。上代側は税込入力のためそのまま。
- **「折数」を追加**(DBには保存しない画面表示専用の計算項目): 上代(定価)を半額にした値を
  参考表示する(例: 定価が半額の際の金額)。ラベル表記は要望により付けない
  (店独自の使い方のため画面上に説明文言は出さない)。
- 実装時にまとめて着手(仕入れ登録画面の作り込みフェーズで一括対応)。

### B-9. 売上の四分類(催事/店頭/メガネ/時計)の自動振り分け(2026-07-15相談)
- 現状: 売上伝票明細表を見ながら「催事」「店頭(メガネ・時計以外)」「メガネ」「時計」の
  4分類を**目視で手動**集計している。
- **相談内容**: これをシステム化するか、Excelマクロ等の外部ツールに任せるか。
- **回答(推奨)**: **トキワ側で自動化するのが筋が良い**。理由は、この分類に必要な情報
  (商品が「メガネ」か「時計」か、大分類コード、購入場所コード=催事かどうか)は
  **移行時点ですでに構造化されたデータとしてDBに入っている**(products.is_glasses、
  大分類名、sales_slips.place等)。Excelマクロは逆に「テキストから分類を推測」する
  必要があり、トキワの構造化データを使うより不正確・保守しづらくなる。
  実装は日報・売上伝票明細表の集計に「四分類の内訳」を追加するだけで済むはずで、
  既存のB-3(マスタ管理)・B-4(検索・分析メニュー)の作業と一緒に進めるのが効率的。
- 分類ルールのたたき台: 時計=製品コード等が時計系 or 大分類名に「時計」、
  メガネ=is_glasses=1、催事=sales_slips.place(購入場所)が店頭以外、
  店頭(メガネ・時計以外)=残り。実データで大分類・場所コードの実態を見てから確定する。

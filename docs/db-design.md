# トキワ DB設計(叩き台)

宝飾ナビのデモデータ(`data/demo/` の11台帳、2026年7月時点)の解析結果と、
それをもとにしたトキワのデータベース設計案。

## 2. 現行構造の特徴と課題(トキワで直す点)

1. **名前の重複保持(非正規化)** — ほぼ全台帳が顧客名・店舗名・担当者名を
   文字列でコピーして持っている。顧客名を変更しても過去データに反映されず、
   表記ゆれの温床になる。→ トキワでは **IDで参照**し、名前はマスターだけが持つ。
2. **伝票の概念が弱い** — 販売台帳は1行=1商品で、同時購入は伝票番号で
   緩くつながっているだけ。→ **売上伝票(ヘッダ)+売上明細(行)** の2階層に分離。
   レジの「会計確定」単位=伝票になり、日報・レシート・返品処理が扱いやすくなる。
3. **固定列の繰り返し** — 顧客メモ01〜10、商品メモ01〜10、備考1/11/21、
   脇石1・2など、枠数固定の列が多い。→ **1対多の子テーブル**にして枠数の制限をなくす。
4. **年度別累計が固定列** — 顧客台帳に「2026年度」「2025年度」…と列が並ぶ。
   毎年列を増やす構造。→ 累計は**売上から集計**して算出(保存しない)。
5. **コード+名称のペア列** — (性別コード, 性別)のような2列ペアが大量にある。
   → 名称は**コードマスター**に寄せる。
6. **サービスポイントとカードポイントが別台帳** — トキワでは
   **ポイント取引テーブル1本**(種別列で区分)+残高はビューで集計。

## 3. トキワのテーブル設計案

マスター系:

- **stores** 店舗(コード, 名称)
- **staff** 担当者(コード, 氏名, 所属店舗, 権限)
- **suppliers** 仕入先
- **code_master** 汎用コード(性別・続柄・購入動機・地区・支払方法など種別+コード+名称)

顧客系:

- **customers** 顧客(ID, 名前, カナ, TEL, 住所, 生年月日, 記念日, ランク, DM可否, 担当者ID, 宝飾/メガネ区分, リングサイズ等)
- **customer_families** 家族(顧客ID, 続柄, 氏名, 生年月日)
- **customer_memos** 顧客メモ(顧客ID, 日付, 本文) ※メモ01〜10を置き換え
- **approach_history** アプローチ履歴(顧客ID, 種別, 内容, 担当者ID, 日時)
  ※ホームの「お声がけ」チェックはここに書き込む

商品系:

- **products** 商品(商品キー, 商品番号, 名称, 分類, 仕入先ID, 仕入単価, 上代, 状態, 保管場所, メガネ品フラグ)
- **product_jewelry** 宝飾属性(商品キー, 地金, 石, 中石重量, 脇石[子テーブル], color/clarity/cut, 鑑別書No)
- **stock_events** 入出庫履歴(仕入・売上引落・返品・棚卸調整)

売上系:

- **sales** 売上伝票(伝票番号, 顧客ID※必須, 担当者ID※必須, 店舗, 販売日, 支払方法, 購入動機, 使用ポイント, 合計)
- **sale_lines** 売上明細(伝票ID, 商品キー※在庫品のみ, 自由入力名※番号なし品, 定価, 買上金額, 割引率, **仕様未定フラグ**)
  ※「レンズ種類未定→後日入力」は仕様未定フラグ+後日更新で実現
- **receivables** 売掛(伝票ID, 頭金, 残高, 最終入金日)
- **receivable_entries** 売掛入出金履歴

ポイント系:

- **point_transactions** ポイント取引(顧客ID, 種別[加算/使用/失効/サービス/調整], ポイント数, 関連伝票ID, 日時)
  ※残高・累計はここから集計

メガネ系:

- **prescriptions** 処方箋(顧客ID, 処方箋No, 用途, 左右SPH/CYL/AX/ADD/PD遠近, フレームサイズ, レンズ商品キー, フレーム商品キー, 合計定価, 合計売値, 対応者ID, 関連売上明細ID)

運用系:

- **sync_queue** オフライン時の未送信キュー(端末ID, 操作種別, ペイロード, 一意キー※二重登録防止, 状態)
- **users / roles** ログインユーザーと権限

## 4. 移行メモ

- 顧客ID・商品キー・伝票番号は現行の値をそのまま引き継ぐ(帳簿の連続性のため)
- 販売台帳→伝票+明細への分割は「伝票番号+販売日+顧客ID」でグルーピング
- 年度別累計は移行時に検算に使う(移行後の集計値と突き合わせて欠損チェック)
- 空の伝票番号(古いデータに多い)は移行時に採番する

## 5. 開発ステップ

1. この設計でSQLite版を作成し、デモデータを流し込む(契約不要)
2. 画面モックをSQLite読み書きの実アプリ化
3. 運用が見えた段階でクラウドDB(+オフライン同期)へ載せ替え

# トキワ クラウド移行 計画メモ

将来トキワをクラウド上のサーバーに載せ、複数店舗・スマホ/iPadからも使えるように
するための方針メモ。**まだ着手しない**(ローカルで精度を上げる段階)。実際に載せる前に
このメモの「公開前チェックリスト」を実装してから移行する。

## 目的(店舗側の希望)
- PC破損(雷・火災・盗難)でデータが消えるのを防ぎたい → クラウドにデータを置く
- 複数PC、将来はスマホ・iPadからも閲覧したい
- 宝飾ナビもクラウド方式なので、同じ形にしたい

## 現状の設計との整合
- トキワは元々クラウド前提で設計を開始(オフライン時の一時退避 sync_queue テーブルを
  用意済み・未実装)。検証のしやすさから今はローカルSQLite単体で開発中。
- サーバーは Python 標準ライブラリ製でスタンドアロン。Linux(VPS)上でほぼそのまま動く。
- SQLite のままでも小規模店舗の同時アクセスは問題なし(将来大規模化時に強化を検討)。

## 法律・責任の整理(個人情報保護法)
- クラウドに個人情報を置くこと自体は合法・標準的(宝飾ナビも同じ)。
- ただし責任は店側に残る: 「安全管理措置」と「委託先(サーバー業者)の監督」は店の義務。
- 「貸金庫」の比喩の限界:
  - VPSは常時ネット接続の"扉のある部屋"。施錠(認証)と鍵の更新(パッチ)を続ける責任がある。
  - 「鍵はこちらだけ」を文字通りにするには**自分で暗号化して預ける**必要がある
    (無暗号だと業者インフラ側から技術的には読める。まともな業者は見ないが物理的に不可能ではない)。
- 国内DCを選ぶことで越境移転の追加手続きは不要。
- ※最終的な法令判断は専門家に確認する前提(ここは一般的理解の整理)。

## 公開前チェックリスト(クラウドに載せる前に必ず実装)
- [ ] **トキワ本体のログイン認証**(現在は素通し。担当者マスタと合わせて実装)。
      強いパスワード + 可能なら2要素。**機械的な定期変更はしない**(下記参照)。
- [ ] **HTTPS**(通信の暗号化。Let's Encrypt等で無料)。
- [ ] **ディスク/データの暗号化**(保存時。「鍵はこちらだけ」を成立させる)。
- [ ] **オフライン同期の実装**(sync_queue を実際に機能させる。通信断でも各店舗は
      営業継続→復旧後に自動送信。今の「オフライン動作を試す」ボタンは見た目デモのみ)。
- [ ] **自動バックアップ**(店舗外にも複製。火災・盗難対策の本命)。

## サーバーを守る3点セット(SSH/OSレベル。パスワード定期変更より効果大)
機械的な月次パスワード変更は現在**非推奨**(NIST/総務省/IPAとも転換済み。
予測しやすい規則化・使い回しでかえって弱くなる)。同じ手間なら以下を実装する:

1. **SSH鍵認証** — サーバーログインをパスワードでなく鍵ファイルで行う。総当たり無効・最強。
   「鍵はこちらだけ」がこれで実現。
2. **2要素認証(MFA)** — パスワード + スマホのコード。漏れても入られない。
3. **自動ブロック(fail2ban等)** — 総当たりを試みるIPを自動締め出し。
- 補助: SSHを全世界に開けず店舗IP等に限定(ファイアウォール)。
- パスワード変更は「漏えいの疑い」「スタッフ退職」等、**きっかけがある時だけ**行う。

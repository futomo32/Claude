# 周辺機器の対応状況と本番機での確認手順

正式運用: Windows PC 1台 + USB接続の周辺機器3点。
会計フロー: ポイントカード読み込み(顧客呼び出し) → レジ → ポイントカード書き込み → レシート印字 → ドロワーオープン

## 機器別の調査結果(2026年7月時点)

### ① レシートプリンター: CITIZEN CT-S601 — ◎ 問題なし

- シチズン・システムズ公式のWindowsドライバーが提供されている
- 標準的なESC/POSコマンド対応で、新アプリからの制御は定番の方法で可能
- 背面に**ドロワーキック端子**があり、DLE EOT / GS a / GS r コマンドでドロワー制御が可能

### ② ドロワー: 品番未確認 — ○ おそらく問題なし(要確認1点)

- フローが「レシート印字→ドロワーオープン」なので、ドロワーは
  **プリンター背面のキック端子(RJ-11、電話線様のコネクタ)経由**の可能性が高い
- この場合、ドロワー自体の型番はほぼ問わない(プリンターが面倒を見る)
- **確認事項**: ドロワーから出ているケーブルの差し先が
  「プリンター背面」なら追加作業なし。「PCのUSBポート直挿し」なら型番の特定が必要

### ③ リライトカードリーダー: スター精密 TCP300II — ⚠ 要注意(最重要)

- Windows用ドライバー・OCXドライバー・サンプルコードは提供されている(制御手段は存在する)
- **ただし2023年6月30日でメーカー販売終了、Windows 11 非対応**(メーカー公表)
- Windows 10はすでにMicrosoftのサポートが終了しており(2025年10月)、
  「Win10のまま使い続ける」は店舗PCとしてセキュリティ上おすすめできない
- 制御方式がOCX(ActiveX)という旧世代技術のため、新アプリからは
  小さな中継プログラムを挟む形になる(実現可能だが開発工数が少し増える)

### TCP300IIへの対応方針(3案)

| 案 | 内容 | 備考 |
|---|---|---|
| A | 本番機(Win11)で動くか実機テストし、動けばそのまま使う | 非対応=動かないとは限らない。ただし故障時の代替機がない |
| B | 後継機/他社のリライトカードプリンターに更新 | 費用がかかるが将来も安心 |
| C | カード書き込みを廃止し「残高はDBが正」方式に変更 | ハード依存が消える。ただしカード券面の残高表示がなくなる運用変更 |

推奨: まずAの実機テスト → 動かない/不安が残る場合にBかCを判断。
Cは修理費用ゼロで恒久解決になるため、カード運用の変更が許容できるなら有力。

## 本番機での確認手順(トキワがなくても今できる)

1. **本番PCのWindowsバージョンを確認** — 設定→システム→バージョン情報。
   Windows 10 か 11 かで③の判断が変わるため最初に確認
2. **CT-S601**: シチズン公式サイトからドライバーを入れ、
   Windowsのプリンター設定から「テストページ印刷」→ 印字されればOK
3. **ドロワー**: ケーブルの差し先を確認(プリンター背面 or PC直挿し)。
   プリンター背面なら、ドライバーのプロパティにあるドロワーキック設定で開閉テスト
4. **TCP300II**: スター製品サポートデータベースからWindowsドライバーと
   ユーティリティを取得し、本番機でカードの読み・書き(リライト)をテスト。
   あわせて本体ラベルの**正確な型番**(TCP342II/TCP352IIなど磁気あり/なしの別)を控える

## レシートが出ない・ドロワーが開かない時の調べ方(2026-08-29 実際に詰まった時の手順)

**上から順に試す。**1つ進むごとに原因の範囲が狭まる。

### 0. まず画面右上を見る

| 表示 | 意味 |
|---|---|
| **🖨 機器ONモード** | サーバーは機器ONで動いている → 1へ進む |
| **🔌 機器OFFモード** | **そもそも送信していない**。起動のしかたが違う → `本番運用で起動.bat` で起動し直す |

機器OFFなのに `本番運用で起動.bat` を使った場合は、**古いサーバーが残っている**可能性が高い。
「トキワ サーバー」の黒いウィンドウを**全部閉じてから**やり直す(v0.34.25 で自動検出するようにした)。

### 1. 動作ログを見る

**設定・マスター → レシート・機器 → 最近の動作ログ**、または `logs\エラー_今日.txt`。

| 記録 | 次に見るところ |
|---|---|
| `レシート 失敗: …` | その文言が原因。2へ |
| `レシート 成功(spooler経由)` **なのに出ない** | **Windowsまでは届いている** → 4(印刷キュー)へ |
| 記録が無い | 会計が完了していないか、機器OFF |

### 2. 部品が入っているか・プリンタ名が合っているか

```
py -3 -c "import win32print; print([p[2] for p in win32print.EnumPrinters(2)])"
```

- **`ModuleNotFoundError`** → `py -3 -m pip install pywin32` を実行してサーバーを起動し直す
- 一覧に **`CITIZEN CT-S601`** が一字一句同じで無い → `server/devices.py` の `PRINTER_NAME` を実際の名前に合わせる

### 3. トキワと同じ経路で単体で叩く

サーバーを通さず、機器制御のコードだけを呼ぶ。**紙は出ない(ドロワーだけ)。**

```
py -3 -c "import sys;sys.path.insert(0,'server');import devices;devices.ENABLED=True;print(devices.open_drawer())"
```

| 結果 | 意味 |
|---|---|
| `{'ok': True, 'via': 'spooler'}` で**開く** | 機器は正常。原因は会計からの呼び出し側 |
| `{'ok': True, 'via': 'spooler'}` なのに**開かない** | 4(印刷キュー)へ |
| `{'error': …}` | その文言が原因 |

### 4. ★印刷キューを見る(2026-08-29 の実際の原因はここ)

**設定 → プリンターとスキャナー → CITIZEN CT-S601 → 印刷キューを開く**

- **ジョブが溜まっている** → プリンタまで届いていない。**プリンタの電源を入れ直す**のが一番早い
- 「一時停止」「プリンターをオフラインで使用する」にチェックが入っていないか

> **2026-08-29 に起きたこと**: 宝飾ナビの古い印刷ジョブがキューに詰まり、その後ろに並んだ
> トキワのジョブが出られなかった。Windowsは受け取っているのでトキワには「成功」と返り、
> 画面上は正常に見えた。**プリンタを再起動して解消。**
> 宝飾ナビとトキワは同じプリンタを共有しているため、片方の詰まりがもう片方を止める。
> 9/2以降は宝飾ナビを使わないのでこの原因は減るが、紙切れ・電源断でも同じ状態になる。
> **「送信は成功しているのに出ない＝キューを見る」**と覚えておく。

### 5. 物理の確認

- ドロワーのケーブルが**プリンタ背面の `DK`(ドロワーキック)の口**に挿さっているか
  (見た目がLANの口に似ているので、LANポートに挿さっていることがある)
- ドロワーが**5番ピン**の配線なら、2番ピン用の今の信号では開かない。試すには:
  ```
  py -3 -c "import sys;sys.path.insert(0,'server');import devices;devices.ENABLED=True;print(devices._send_to_printer(b'\x1bp\x01\x19\xfa'))"
  ```
  これで開けば5番ピン。`devices.py` の `DRAWER_KICK` を差し替える。

### 参考: COMポートについて

```
COM7 : ctvrcom Virtual Communication Port   ← CITIZENのドライバが作る仮想COM
COM3 : SMJ USB Device                       ← カードリーダー(TCP300II)
```

**COM7はドライバ本人が握っているので、直接開こうとすると「アクセスが拒否されました」になる。**
これは異常ではない。トキワは通常**Windowsのプリンタ(スプーラー)経由**で送るので問題ない。
`機器テスト.bat` は**わざとCOMを直接叩く**作りなので、この構成では必ず失敗する。
**テストが失敗しても機器が壊れているわけではない。**

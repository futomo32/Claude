# バックアップと復元(2026-07-30 実装)

トキワのデータは **`db/tokiwa.db` の1ファイル**にすべて入っている。このファイルを失うと
顧客・売上・ポイント・在庫の全てが消える。データ消失対策はトキワを作った元々の動機であり、
正式運用開始の絶対条件。

> **最重要**: バックアップは「取れていること」ではなく「**戻せること**」で意味が決まる。
> 年に一度は復元の練習をすること(手順は後半)。

## 仕組み

| 何を | どこで | 内容 |
|---|---|---|
| 実処理 | `server/backup.py` | オンラインバックアップAPI・整合性チェック・世代管理・複数保存先 |
| 自動実行 | `server/app.py` の `backup_daemon()` | サーバー起動中に1日1回。10分ごとに日付が変わったかを確認 |
| 手動実行 | 設定 → バックアップ →「今すぐバックアップ」 | 管理者のみ |
| 手動実行(コマンド) | `python3 scripts/backup_db.py` / `バックアップ.bat` | タスクスケジューラ登録用 |
| 設定 | 設定 → バックアップ(app_settings に保存) | ON/OFF・店外の保存先(最大5か所)・世代数 |

### 設計上のポイント(なぜこうしているか)
- **オンラインバックアップAPI** … WALモードのままファイルをコピーすると取りこぼす恐れがある。
  この方式なら営業中・サーバー起動中でも一貫性のあるコピーが取れる。
- **整合性チェック(`PRAGMA integrity_check`)** … コピー直後に必ず確認し、壊れていたら
  そのバックアップを破棄して失敗として記録する。「取れているつもり」が最悪のパターンのため。
- **店内(`db/backups`)には常に保存** … 店外の保存先が繋がっていなくても控えは残る。
- **店外にも複製** … 火災・盗難・PC故障で店内の複製ごと失うのを防ぐ。ここが本番の保険。
- **世代管理(既定14世代)** … 1世代だけの運用は危険。DBが壊れた状態やランサムウェアで
  暗号化された状態で上書きすると復旧不能になる。複数世代あれば壊れる前まで戻れる。
- **削除は自分のファイルだけ** … 世代削除の対象は `tokiwa_YYYYMMDD_HHMMSS.db` に一致する
  ものだけ。ユーザーが指定したフォルダの他のファイルには絶対に触らない。
- **`db/backups/` は .gitignore 済み** … バックアップは実顧客データを含むため、
  絶対にGitHubへ上げない。

## 初期設定(正式運用の前に必ず)

1. トキワを起動し、**管理者**でログイン
2. 設定 → **バックアップ**
3. 「自動バックアップを使う」をONにする
4. **店外の保存先**を1行に1つ入力(最大5か所)。例:
   ```
   D:\トキワバックアップ
   C:\Users\(ユーザー名)\OneDrive\トキワバックアップ
   ```
   - 外付けHDD・USBメモリのフォルダ、または OneDrive / Dropbox / Googleドライブの
     **同期フォルダ**を指定する(同期フォルダに置けば自動でクラウドにも複製される)
   - **店外を1か所も指定していないと、火災・盗難・PC故障で全部失う**。必ず1つは設定する
5. 世代数(既定14)を確認 → 「設定を保存」
6. 「今すぐバックアップ」を押し、下の「保存されている控え」に店内・店外の両方が出ることを確認

### 閉店後にも確実に取りたい場合(任意)
自動バックアップはサーバー起動中しか動かない。閉店後や休業日にも取りたい場合は
`バックアップ.bat` をWindowsのタスクスケジューラに登録する。

1. タスクスケジューラを開く → 「基本タスクの作成」
2. 名前: `トキワ バックアップ` / トリガー: 毎日・時刻を指定(例 20:00)
3. 操作: 「プログラムの開始」→ プログラムに `バックアップ.bat` のフルパスを指定
4. 「開始(オプション)」にトキワのフォルダを指定する(相対パスで動くようにするため)

## 復元のしかた(データが壊れた・消えた時)

**慌てて上書きしないこと。** 今の `tokiwa.db` も証拠として残す。

1. **トキワ(サーバー)を止める** — 起動中のコマンドプロンプトで `Ctrl+C`。
   ※動いたまま上書きすると壊れる
2. **今の `db/tokiwa.db` を退避** — 削除せず `tokiwa_壊れた_20260730.db` のように改名して残す
   (原因調査に使える。容量に余裕があれば消さない)
3. **戻したいバックアップを選ぶ** — `db/backups/` または店外の保存先から
   `tokiwa_YYYYMMDD_HHMMSS.db` を選ぶ。**壊れた原因が分からない場合は、いきなり
   最新ではなく「確実に正常だった日」のものを選ぶ**(壊れた状態がバックアップされている
   可能性がある)
4. **コピーして名前を変える** — 選んだファイルを `db/` にコピーし、`tokiwa.db` にリネーム
   (元のバックアップファイルは保存先に残したまま。移動ではなくコピー)
5. **トキワを起動** — ログインして顧客数・最近の売上・ポイント残高を確認
6. **戻した分の入力をやり直す** — バックアップ時点以降の会計は消えている。
   レシートの控えや手書き伝票から再入力する(レジは過去日付での登録に対応している)

### 復元の練習(年1回)
本番の `db/tokiwa.db` は触らずに練習できる。

1. バックアップファイルを別のフォルダにコピーし、`tokiwa.db` にリネーム
2. `python3 server/app.py` のDBパスを一時的にそのフォルダへ向ける、または
   トキワのフォルダごと別の場所にコピーして、そちらの `db/tokiwa.db` に置く
3. 起動して中身が見えることを確認 → 確認できたら練習用フォルダを削除

## 運用中の確認(月1回でよい)

- 設定 → バックアップ の「最終バックアップ」が**当日または前営業日**になっているか
- 「保存されている控え」に**店外の保存先が出ているか**(⚠ 読めません と出ていたら
  外付けHDDが外れている・クラウドの同期が止まっている)
- 外付けHDDを使っている場合は、**HDD自体の故障**にも備えて2か所以上が理想

## 既知の制約

- 自動バックアップは**サーバー起動中のみ**動作する(営業時間に1回は取れる想定)。
  閉店後・休業日も確実に取るならタスクスケジューラを併用する
- **商品写真(`data/real/images/`)はこのバックアップに含まれない**。DBのみが対象。
  写真も守る場合は、フォルダごとクラウド同期フォルダに置くか別途コピーする
- 保存先がネットワークドライブの場合、切断時はスキップされる(店内の控えは残る)
